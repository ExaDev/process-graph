# @exadev/process-graph-store-sqlite

[![GitHub](https://img.shields.io/badge/GitHub-181717?logo=github&logoColor=white)](https://github.com/ExaDev/process-graph) [![CI](https://img.shields.io/github/actions/workflow/status/ExaDev/process-graph/ci.yml?branch=main)](https://github.com/ExaDev/process-graph/actions)

A private workspace package, not published on its own: it is bundled into [`process-graph`](../../../targets/process-graph/README.md), which exposes it as `process-graph/store`, beside the store contract.

The `GraphStore` port from `@exadev/process-graph-store-contract` on SQLite through [Drizzle](https://orm.drizzle.team). It is written against Drizzle's async SQLite database type, so any Drizzle SQLite driver plugs in: `@exadev/process-graph-sqlite-node` supplies `node:sqlite`, `@exadev/process-graph-sqlite-wasm` supplies SQLite in a browser worker on OPFS. `src/` imports nothing Node-only.

```ts
import { createGraphStoreRouter } from "@exadev/process-graph-store-contract";
import { createSqliteGraphStore } from "@exadev/process-graph-store-sqlite";
import { createRouterClient } from "@orpc/server";

const store = createRouterClient(
  createGraphStoreRouter(createSqliteGraphStore({ db })),
);
```

## Schema

`src/tables.ts` is the one table definition. Every record a model declares is a row keyed by model id and record id, with a `position` column keeping the declared order; enumerated columns take their values from graph-schema's own vocabulary, and nested values are JSON text. Rows never reach the contract: `src/rows.ts` flattens a model into rows and reassembles it, parsing the result with graph-schema's `modelSchema`, so what leaves the store is checked to be a model. A unit test derives the row schemas with `drizzle-orm/zod` and asserts they agree with the model schema on every shared scalar field.

Relations kept beside a model (`child-of`, `assigned-to`, `part-of`) are rows of their own, keyed by model, kind and both ends so a relation sent twice is stored once, with a position keeping the order they were first stored. A model's fact record is two tables beside the overlay: `artefact_facts`, one row per artefact whose provision is known with a boolean `provided`, and `named_facts`, one row per named fact with its trilean value as JSON text, parsed with the contract's `factRecordSchema` on every read. An artefact or name with no row is unknown. Each transition row records whether graph-domain's `loopTransitions` counts it as a decision's loop edge, so the structural queries can leave loop edges out without loading the model. No foreign keys are declared, because SQLite enforces them only on connections that enable them; the store writes and deletes a model's rows together in one transaction instead.

## Migrations

The SQL migrations under `drizzle/` are generated by drizzle-kit from `src/tables.ts` and committed: once data exists they are the schema's history. After changing the tables, run `pnpm run migrations:generate` and commit the new folder.

The build embeds them in the package (`scripts/embed-migrations.ts`, parsed by drizzle's own `readMigrationFiles`; the generated module is build output and never committed), and `migrate` applies the missing ones in one transaction, recording each in drizzle's `__drizzle_migrations` journal by the same name and hash drizzle's migrators use. The store migrates on its first operation. Drizzle's own migrators cannot serve every runtime: `drizzle-orm/migrator` reads the folder through `node:fs`, which a browser worker does not have, and `migrateAsync` reads its journal in object mode, which the `sqlite-proxy` session refuses. A unit test checks that `migrate` builds the same schema and journal as drizzle's `node-sqlite` migrator reading the committed folder, and that each finds nothing left to apply after the other. The decision and the evidence are in [#22](https://github.com/ExaDev/process-graph/issues/22).

## Writes and queries

Every write runs `checkStored` (and `factIssues` for the facts it keeps) from the contract before it commits, takes the next value of the store-wide revision sequence, rewrites the model's rows in one transaction and publishes the change to the store's `ChangeFeed` once it has committed. A failed check or an aborted signal rolls the transaction back.

`query.ready`, `query.blockedChain` and `query.impact` are single `WITH RECURSIVE` queries through Drizzle's `sql` template over `transitions`, `elements` and `overlay`, with the contract's semantics (control elements passed through, loop edges left out, traversal stopping at done work). `query.descendants` and `query.ancestors` are the same kind of query over the `child-of` rows of `relations`, and `query.children` a plain one. The walks cap distances at the model's element count, which is longer than any shortest path and ends the recursion on a cycle no decision closes, or a cycle of `child-of` relations.

Transactions are opened with plain `BEGIN IMMEDIATE`, `COMMIT` and `ROLLBACK` statements rather than Drizzle's `transaction`, whose callback has to be synchronous on a synchronous driver and asynchronous on an async one. Each store operation therefore runs with the connection to itself: by default the store serialises its own operations, and a host that shares the database across contexts passes `exclusive` to hold its cross-context lock as well, and `feed` to bridge the other contexts' changes.

## Tests

The contract's conformance kit runs against the store over `node:sqlite` in memory, and further tests cover reopening a database file, the migrations and the row schemas.
