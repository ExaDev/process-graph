# Contributing

## Adding a package

A new package is private and reaches consumers through a subpath of the published `process-graph` package, which bundles it. It needs no name on npm and no trusted publisher.

1. Pick the layer: `packages/core/<domain>/<name>` for the model, its analysis and ports; `packages/adapters/<domain>/<name>` for an implementation of a port against one external system; `packages/ui/<domain>/<name>` for components; `packages/targets/<name>` (flat) for a deployable entry point.
2. Copy the closest existing package's shape: `package.json` (`exports` map, script set), `tsconfig.json` plus `tsconfig.build.json` (and `tsconfig.node.json` for an isomorphic package), `eslint.config.ts`, `vitest.config.ts`, `stryker.config.ts`, `test/package.smoke.test.ts`.
3. Name it `@exadev/process-graph-<name>`, mark it `"private": true`, and set `version` to `0.0.0` and `repository.directory` to the package's path. Give it no `publishConfig`.
4. Add dependencies with pnpm: a sibling as `workspace:*` (`pnpm add @exadev/process-graph-<sibling>@workspace:*`), and a third-party library from the catalog in `pnpm-workspace.yaml` (`pnpm add --save-catalog <library>@<exact version>`, which adds the catalog entry when there is none). `pnpm run deps:lint` rejects anything else.
5. Add its `tsconfig.build.json` to the root `tsconfig.build.json` `references`.
6. If it is the first package in its layer, add that layer's workspace entry to `knip.config.ts` (an entry that matches nothing is a knip hint).
7. Expose it through `process-graph`, in `packages/targets/process-graph`: a module under `src/` that re-exports it, named for the subpath (`src/<subpath>.ts`), an entry for that module in `tsdown.config.ts`, the subpath in the `exports` map, the module in the subpath list in `eslint.config.ts`, a case in `src/entrypoints.unit.test.ts` and an import of the subpath in `test/package.smoke.test.ts`. Add the package to `devDependencies` at its exact version (`pnpm add -D --save-exact @exadev/process-graph-<name>@<version>`), never `workspace:*`, since that manifest is published as written. Each third-party library the new subpath needs that the root entry does not goes in `peerDependencies`, marked optional in `peerDependenciesMeta`, as a caret range on the catalog's version, `^<version>`, or at the catalog's exact version when that is a prerelease, which has no compatible-range semantics (`pnpm add --save-peer --save-exact <library>@<version>`, then widen a stable peer's specifier to the caret range; `deps:lint` holds both forms). Where a layer's names collide with another layer's on the same subpath, namespace one layer rather than shadow a name.
8. Write its `README.md`, then `ln -s README.md AGENTS.md && ln -s README.md CLAUDE.md`.
9. Add it to the internal packages table in the root `README.md`, and the subpath to the `process-graph` README.
10. Verify with the repository scripts: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:smoke`, `pnpm exec knip`, `pnpm run deps:lint`.
11. Commit as `feat: add <name> package`, describing the package's role and any deliberate decision, not the process that produced it.

## Release strategy

Only `process-graph` is published. `release-workspace.config.ts` configures [`@exadev/semantic-release-workspace`](https://github.com/ExaDev/semantic-release-workspace), which the `release` job in `.github/workflows/ci.yml` runs as `pnpm release` on every push to `main` once the other jobs have passed.

- The orchestrator discovers the packages from `pnpm-workspace.yaml`, orders them by their dependencies on one another, `devDependencies` included, and releases each after every sibling it depends on, so `process-graph` is released after every package it bundles.
- A package's release is decided from the commits that touched its own directory, using the types and release levels in `commit-types.ts`. A commit that touches no package directory releases nothing, and a commit scope has no effect on which package releases.
- Every package gets a `<name>@<version>` tag, which the orchestrator reads to find its last release. A private package gets nothing else: it runs only `@semantic-release/npm`, which bumps its version and skips publishing because the manifest is private, so it writes no `CHANGELOG.md` and creates no GitHub Release. `process-graph` gets its `CHANGELOG.md`, its GitHub Release and its npm publish.
- When a package releases, every dependent's range on it is rewritten to the new version where the range names one, the lockfile is regenerated, and the dependent releases a patch even if nothing else about it changed. `process-graph` names each bundled package's exact version in `devDependencies`, so a change confined to a private package's directory still releases `process-graph`, as a patch, carrying the new bundle. A feature in a private package therefore reaches consumers in a `process-graph` patch release unless a commit touching `process-graph` itself says otherwise.
- The whole run's version bumps, changelog entries and dependency-range rewrites are committed once and pushed atomically with the tags before anything is published.
- Publishing uses npm trusted publishing (OIDC): `id-token: write` on the job, no `NPM_TOKEN`, and no `registry-url` on `setup-node`, because that writes a token line that wins over the OIDC exchange. `@semantic-release/npm` publishes with `npm publish`, which ships every specifier as written, which is why the `process-graph` manifest uses literal versions where the private ones use `catalog:` and `workspace:*`.
- The release commit and tags reach the protected `main` through a repository deploy key with write access (the `RELEASE_DEPLOY_KEY` secret), which the `main` ruleset lists as a bypass actor; `GITHUB_TOKEN` cannot bypass a ruleset. The `release` job checks out without persisting a credential, writes the key to the runner's temporary directory only in the step before the release, and removes it afterwards. The orchestrator pushes with plain `git push origin`, so the release step rewrites https GitHub URLs to SSH through git's per-process config and sets `GIT_SSH_COMMAND` to use only that key; `GITHUB_TOKEN` stays in that step's environment for the GitHub API calls that create releases and comment on issues and pull requests.

Release configuration lives only in `release-workspace.config.ts`. The orchestrator sets the tag format, plugins and analysis options on every per-package run, so a `release.config.*` inside a package would be overridden rather than honoured.

To see what a run would do without tagging, committing, pushing or publishing, run `pnpm release --dry-run` from the root on a clean tree and a pushed branch, with `--branches <branch>` naming it and a `GITHUB_TOKEN` in the environment.
